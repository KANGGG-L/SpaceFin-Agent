## 1. 验收环境与运行态说明

- **合成种子**：`seed/generate_seed.py` 生成，**广东 21 城 DWD 对齐版**，200 笔贷款 / 200 笔抵押物 / 200 位客户（与 AC-02 同批种子）。
- **业务库**：`spacefin`（loan / collateral / customer），变更写入走 MySQL 容器（时区 **+08:00**）；宿主为 **UTC**（`cdc-downstream.md` §4 已记录的第三方时区差异，本次计时用宿主机 wall-clock，不涉时区换算）。
- **ODS 载体（判定载体）**：
  1. `spacefin_crawler.ods_cdc_log`（SQL 可查的变更事件表，`before_json/after_json/cdc_ts`，CDC 捕获进程实时写入）；
  2. 数据湖 `data_lake/cdc/ods/{table}/dt=*/{seq}.jsonl`（逐事件追加，`dt=` 目录按**宿主机 UTC 日期**命名）。
- **运行态备注（诚实记录）**：常驻进程为两个实际运行实例——CDC 捕获进程 `main.py`（PID 468181，2026-08-04 20:10 UTC 启动）与消费进程 `consumer.py`（PID 483447，2026-08-04 21:27 UTC 启动），均早于 2026-08-05 落地的 S6「位点持久化」代码（`ods_cdc_position`）；故这两个常驻进程按旧版代码运行——**ODS 捕获（本 AC 验收线）正常**，但位点表 `ods_cdc_position` 不推进（该表现在仅有的 1 行位点记录是 S6 验证时独立调用写入，非上述常驻进程产生），属 S6/运维域的运行态观察，不在 AC-01 范围内。本验收只对这两个常驻进程的**实际 ODS 捕获行为**做独立测量，不重启服务、不改动代码。

## 2. 验收方法（独立执行路径）

**口径定义（与 PRD 一致）**：业务库任意一笔 `loan`（或 collateral）主档变更，应在 ≤10s 内以 `UPDATE` 事件形式出现在 ODS（`ods_cdc_log` 新行 + 数据湖新 JSONL），且**同一变更只出现 1 条**（无误重）。ODS 贴源不解释——`after_json` 应携带变更后全量字段（含余额新值）。

**独立实测步骤**（脚本 `/tmp/ac01_cdc_test.py`，运行环境 `~/miniforge/envs/spark/bin/python`）：

1. **不读 DWS/ADS 结果**：仅连接 `spacefin`（业务库）与 `spacefin_crawler`（ODS 日志表），对变更与 ODS 事件做端到端观测。
2. **记录变更前水位**：`ods_cdc_log` 当前 `MAX(id)`（实测 4071），作为观测窗口起点。
3. **发起业务库变更**：对 `loan 30199` 执行 `UPDATE balance = 153089.47 → 154089.47`（+1000.00），`autocommit` 即时提交，记录 wall-clock `T0`。
4. **轮询 ODS 可见**：以 0.3s 间隔查询 `ods_cdc_log` 中 `id > 水位` 且 `after_json.loan_id = 30199` 的 `UPDATE` 事件，命中时记录 `T1`；**连接使用 autocommit=True**——否则 InnoDB REPEATABLE READ 会在首条 SELECT 建立读快照，后续轮询永远看不到 CDC 新写入的行（首次实测踩坑后修正，见 §4）。
5. **无重复校验**：统计观测窗口内 `loan 30199` 的事件条数，应恰为 1。
6. **数据湖落盘校验**：在 `data_lake/cdc/ods/loan/dt=*/` 中查找该事件的 JSONL 文件，确认与 `ods_cdc_log` 同批写入。
7. **回滚**：变更验证完毕后恢复原余额（产生第 2 条事件，作无误重旁证），恢复环境原状。

## 4. 说明与坑位记录

- **首次实测曾出现「30s 未见事件」的误报**：原因是轮询连接的 PyMySQL 默认 `autocommit=False`，InnoDB REPEATABLE READ 在首条 SELECT 建立了读快照，之后同一事务内永远读不到 CDC 新写入的行。修正为 `autocommit=True` 后复测，事件在 0.32s 内即被轮询命中；同时事后按 `cdc_ts` 核对，首次事件实际与变更同秒写入（id=4070），即 CDC 捕获本身无延迟，是观测脚本的隔离级别问题。
- **时区说明**：`ods_cdc_log.cdc_ts` 为 MySQL 服务器时区（+08:00），数据湖 `dt=` 目录与文件内 `ts` 为宿主 UTC——两端时间戳相差 8 小时属文档已记录的部署差异（cdc-downstream.md §4），判定只使用 wall-clock 差值。
- **Doris 侧查证**：Doris（spacefin-doris-fe:9030）存在 `ods.ods_cdc_log` 镜像表（实测时 2869 行），由湖同步链路**批量刷新**，测试事件不即时出现；AC-01 的 ODS 可见性判定载体为 MySQL `ods_cdc_log` 与数据湖 JSONL（与 cdc-downstream.md §6 一致）。
- **运行态影响**：实测期间消费端把 +1000 快照瞬时写进 `ads_risk_class(stat_date=2026-08-05)`（常驻消费端为旧版 UTC 业务日期逻辑，属 cdc-downstream.md §4 已知时区坑）；测试后已从 `dws_risk_class` 现状聚合**修复**该行（见 AC-05 记录 §1 备注），当前三出口一致。

## 5. 结论

- **AC-01 验收通过**：业务库 `loan` 变更 → ODS 可见延迟 **0.32s**（≤10s 秒级），同一变更 ODS 恰 1 条**无误重**；数据湖 ODS 与日志表同秒落盘，`after_json` 为变更后全量贴源数据。
- 旁证：回滚变更同样秒级可见且无误重；下游消费端追平水位，增量重算幂等。
- 备注：实测覆盖 `loan` 表变更；`collateral/customer` 变更的捕获语义相同（同一 CDC 捕获进程与写入路径），并由既有 CDC 单元/集成测试覆盖，不在本次独立实测观测范围内。
