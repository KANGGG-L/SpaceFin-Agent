# 阶段 2：技术可行性评估（Technical Feasibility）

> **阶段目标**：在阶段 0（机会成立）与阶段 1（需求与优先级已定）的基础上，回答本仓库核心决策问题——**技术上是否可行、风险在哪**。
> **本阶段交付物**：技术可行性评估 + 效果基线；**开发产出**：数据底座 PoC 代码（见 [PoC 说明](../poc/data-foundation/README.md)）。
> **状态**：✅ 已完成

---


## 1. 阶段衔接与待回答的问题

本阶段承接两条上游结论：

- **阶段 0 的生死假设**：H1（空间模型显著优于全局基线）、H3（合成画像与真实不良率分布对齐）、H5（数据合规可得）。只要一条证伪，方向需调整。
- **阶段 1 的优先级**：RICE 排序 P0 = 集成 AVM + 空间风险推演，P1 = 合成仿真 + 沙盒，P2 = RegTech。阶段 2 的技术评估按此优先级展开，先证 P0 可行性。

本阶段必须回答三个问题：**（1）每个能力是否有成熟、可落地的技术路径？（2）候选方案里我们排除了什么、为什么？（3）效果基线设在哪里、由谁在哪一阶段验证？**

### 评估方法

可行性不以"技术上能做"为满足，而以"在单人作品 / 小团队交付边界内可演示、可度量"为准（回应路线图 R4"工程可行性过高"风险）。证据来源分三层：

1. **架构与文献证据**：公开工业级组件与行业成熟实践。
2. **PoC 实证**：数据底座 PoC（`poc/data-foundation/`）对 H1 做最小可运行论证。
3. **排除论证**：对每条被否决的候选方案记录否决理由，避免"全都要"陷阱。

## 2. 需求驱动的技术选型决策

本阶段的技术选型不是先验的"技术偏好"，而是从阶段 0 的痛点（P1/P2/P3）与阶段 1 的 RICE 优先级（P0: AVM+空间推演 / P1: 仿真沙盒 / P2: RegTech）反向推导而来。下表逐条展示了"业务需求提出什么挑战 → 这个挑战要求技术满足什么条件 → 据此做的选型决策"。

### 2.1 需求 → 技术决策链路

| # | 业务需求（来自阶段 0/1） | 派生的技术挑战 | 对技术的硬性要求 | 最终选型 |
|---|------------------------|-------------|----------------|---------|
| R1 | 抵押物估值"滞后、主观、易道德风险"，需 T+月批次自动化重估（P1 痛点） | 同一城市内不同片区价格变动速度不一——全局模型给全城同一个系数，必然在局部失真 | 模型必须支持**空间非平稳性**——每个自变量在不同区域可以有不同系数（带宽自适应） | MGWR + GBDT 混合架构 |
| R2 | 风控只看"人+钱"，缺"地+境"维度，无法量化抵押物空间风险（P2 痛点） | 亿级借款人坐标 × 数万统计区/学区/高危多边形做拓扑计算，单机根本跑不动 | 必须**分布式原语**处理空间连接、投影、距离计算 | Apache Sedona（PySpark） |
| R3 | 借款人真实生存环境被 LLM 美化，画像不可信（P3 痛点，H3 生死假设） | 通用 LLM 直出存在社会期望偏见，必须有一个"说真话"的裁判机制 | 生成器必须有**外部事实对照机制**——不是"写得像就行"，而是"与真实分布同构" | PerGent 生成-批评估闭环多智能体 |
| R4 | 多源异构数据（信/行为/房产/地理）口径不一，1104 G11 报送易出错（路线图 Phase 0） | 业务库、日志、外部数据源格式各异，全量搬迁成本极高且口径不一致 | 存储与查询必须**分冷热、免搬迁联邦查询**，统一口径 | 湖仓一体（Hive+Doris+Multi-Catalog） |
| R5 | 事中反欺诈要求秒级响应（路线图 Phase 1） | T+1 批处理对"1 小时内同备注册超阈值"这类模式完全失效 | 必须**流式 + 时间窗 + Exactly-Once** | Kafka + Flink CEP |
| R6 | 金融 AI 必须可审计、可解释、合规可报（路线图 R3 风险 + 护栏指标） | 风控模型输出要能追溯到特征归因、变量不能含歧视性维度 | 输出必须附带**可解释报告**，合规检索需**毫秒级定位** | 倒排索引 + 特征归因 + 1104 模板 |

### 2.2 需求-能力映射（按 L0–L5）

下表展示每层技术组件解决的具体痛点与对应阶段 0 假设。这是"为何是这个组件、而非那个"的核心论证。

| 层级 | 技术组件 | 解决的痛点 | 验证的假设 | 如果这个组件选错了，会怎样 |
|------|---------|-----------|-----------|---------------------------|
| L0 | Hive+Doris+Multi-Catalog | P1: 多源口径不一对不齐；P2: 空间数据与信贷数据割裂 | H5（数据合规可得） | 报表口径不一致 → 1104 报送出错 → 监管处罚 |
| L1 | Kafka+Flink CEP+Redis | P2: 事中拦截缺失；路线图 Phase 1 反欺诈需求 | H1（空间特征提升风控识别力） | 反欺诈窗口判定仍需人工 → 错过拦截窗口 |
| L2 | Apache Sedona（PySpark） | P2: 空间维度缺失无法量化"高危区域"惩罚项 | H1（空间模型优于全局基线） | 亿级坐标单机崩溃 → 空间风控退化为"有概念、无执行" |
| L3 | MGWR+GBDT 混合架构 | P1: 估值滞后、主观、易道德风险 | H1（R² 提升 ≥ 10pp） | 全局模型估值失真 → AVM 不如人工 → 无法替代人工 |
| L4 | PerGent 生成-批评估闭环 | P3: 画像被 LLM 美化，真实风险被粉饰 | H3（KS ≤ 0.05） | 仿真输出不可信 → 策略研究员弃用 → 沙盒空转 |
| L5 | 1104 模板+倒排索引+可解释 | P2: 策略决策缺乏审计追溯；路线图 R3 合规风险 | (护栏指标，非假设) | 模型黑盒被监管叫停 → 产品合规性坍塌 |

## 3. 能力可行性评估（L0–L5）与技术对比

按路线图能力地图，自底向上逐层评估。每一层均给出**（A）候选方案 → 选型与排除 → 风险 → 验证**的思考链路，并在下方附**（B）三方案多维度对比表**（至少两个替代方案与终选方案在 5 个维度上系统比较）。

### 3.1 L0 数据底座（湖仓一体）

| 维度 | 内容 |
|------|------|
| 决策问题 | 多源异构（信贷业务库 / 行为日志 / 房产空间 / 地理基准）如何统一存储与查询？ |
| 候选方案 | A. 全量迁入单一数仓；B. 纯数据湖（Hive/对象存储）；C. **湖仓一体（Hive 冷存 + Doris 热存 + Multi-Catalog 联邦查询）** |
| 选型与排除 | 排除 A（搬迁成本高、链路长）；排除 B（交互查询延迟高、难支撑 BI 驾驶舱）。选 C：Hive 承载十年全量冷数据（Parquet/ORC），Doris 承载 ADS 热表与实时预警，Multi-Catalog 免搬迁联邦查询，整体成本降约一半 |
| 主要风险 | Doris 集群运维门槛；多源权限与血缘治理 |
| 验证 | PoC 验证分层（ODS/DWD/DWS/ADS）与联邦查询可行性；生产以 3 家试点行接入为里程碑 |

**多维度技术对比**

| 维度 | A. 全量单仓（Greenplum/Teradata 模式） | B. 纯数据湖（Hive+Spark） | C. 湖仓一体（Hive+Doris+Multi-Catalog）**←终选** |
|------|----------------------------------------|---------------------------|--------------------------------------------------|
| 性能 | 并发高但同构数据；异构源搬迁后查询仍慢于原生 | 交互查询延迟高（秒级→分钟级），无法支撑 BI 驾驶舱 | 冷热分离——Hive 批量 ETL 分钟级，Doris OLAP 秒级 |
| 可维护性 | 需专人运维 MPP 集群，扩容成本高、搬迁链路长 | 仅需维护 Hive/Spark，但报表/BI 需外挂查询引擎（多一套运维） | Hive 冷存免运维，Doris 热层自管理压缩/副本；Multi-Catalog 免搬迁 |
| 社区生态 | Greenplum 已停止主版本演进（开源版）；Teradata 封闭 | Hive+Hadoop 生态成熟，但实时查询社区活跃度下降（被 Doris/ClickHouse 分流） | Doris Apache 顶级项目，与 Spark/Flink/BI 工具全部对接，中文社区活跃 |
| 学习成本 | MPP 概念需 DBA 背景；新成员上手慢 | 仅需 SQL + HiveQL，学习曲线低 | Hive 侧零新增成本；Doris 兼容 MySQL 协议，BI 工具直连，无额外学习 |
| 扩展性 | 纵向扩展为主，横向加节点成本高 | 天然水平扩展（HDFS），但查询延迟不随节点线性改善 | Hive 冷数据无限扩展；Doris 热节点水平线性扩展，且 BE 节点可独立扩缩 |

**核心选择逻辑**：金融场景需要"历史全量查询 + 实时驾驶舱"双模式，纯湖不能满足实时、纯仓搬迁成本太高。湖仓一体是唯一同时满足"冷数据低成本存储"和"热查询秒级响应"的方案。

### 3.2 L1 实时风控（流批一体）

| 维度 | 内容 |
|------|------|
| 决策问题 | 事中反欺诈与实时指标如何做到秒级？ |
| 候选方案 | A. 纯批处理 T+1；B. **Kafka + Flink CEP + Redis 缓存**；C. Spark Streaming 微批次 |
| 选型与排除 | 排除 A（无法满足"事中拦截"）；排除 C（微批次天然有数百 ms~数秒延迟，且 CEP 复杂事件定义不如 Flink 原生）。选 B：Flink 消费 Kafka 行为流，CEP 定义时间窗序列规则（如 1 小时内同设备注册超阈值），Exactly-Once 写入实时数仓，高危信号回调授信系统 |
| 主要风险 | 规则误杀率；Binlog 采集对业务库的压力（以 CDC 而非全量轮询缓解） |
| 验证 | 反欺诈命中率 / 误杀率基线在阶段 6 评估测中确立 |

**多维度技术对比**

| 维度 | A. 纯批处理 T+1 | B. Kafka+Flink CEP **←终选** | C. Spark Streaming 微批次 |
|------|----------------|------------------------------|---------------------------|
| 性能 | 次日才能响应，无法用于事中拦截 | 毫秒级延迟，Exactly-Once 语义；Flink CEP 原生支持复杂时间窗模式匹配 | 数百毫秒至数秒的微批次延迟，对"同设备 1 小时内多注册"的时间窗判定不够精确 |
| 可维护性 | 最简单——无流式管道，仅定时调度 | Flink 有状态后端（RocksDB）需调优；Kafka 集群运维为团队常态技能 | Spark 批流一体降低概念复杂度，但微批次 checkpoint 开销大 |
| 社区生态 | 不适用（不是流式方案） | Flink 为流式计算事实标准，Kafka 生态成熟；两者均有丰富的中文文档与故障案例 | Spark 社区最大，但流式功能长期被视为批处理的附属而非一等公民 |
| 学习成本 | 零学习成本 | Flink CEP DSL 需专门学习时间窗语法；状态管理与水位线概念有入门门槛 | 如果团队已用 Spark 做批处理，学习成本几乎为零 |
| 扩展性 | 不适用 | Kafka 分区 + Flink Task Slot 线性扩展；Flink 可动态扩缩 TaskManager | 受 Spark 批处理架构约束，微批次扩展不如 Flink 流式原生灵活 |

**核心选择逻辑**："同设备 1 小时内多次注册"这类反欺诈规则天然是时间窗序列模式。Spark Streaming 的微批次被时序精度限制，批处理直接不适用。Flink CEP 是唯一同时满足"秒级响应用"和"复杂事件模式定义"的方案。

### 3.3 L2 空间风控（分布式空间计算）

| 维度 | 内容 |
|------|------|
| 决策问题 | 亿级坐标点 × 数万统计区多边形的拓扑计算如何不崩？ |
| 候选方案 | A. 单机 PostGIS / GeoPandas；B. **Apache Sedona（PySpark 分布式空间计算）** |
| 选型与排除 | 排除 A：单机在亿级交叉运算下内存溢出。选 B：Sedona 注入 Geometry/R-Tree 空间索引，ST_Transform 做坐标投影，ST_DistanceSphere（跨城大圆距）/ 平面笛卡尔距（同都会通勤）按尺度选择；S2 优化 Spatial Join 分钟级完成住址 × 高危多边形相交 |
| 主要风险 | GeoPandas 单线程 fallback 仅适用于演示样本；真实规模须集群 |
| 验证 | PoC 在小样本验证空间连接逻辑；生产规模在阶段 3 原型中压测 |

**多维度技术对比**

| 维度 | A. 单机 PostGIS/GeoPandas | B. Apache Sedona (PySpark) **←终选** | C. GeoMesa (Accumulo/HBase) |
|------|---------------------------|--------------------------------------|------------------------------|
| 性能 | 千万级以可接受；亿级 Spatial Join 内存溢出 | 分布式 R-Tree 索引 + S2 优化，亿级点 × 万级多边形分钟级完成 | 分布式索引能力强，但写入吞吐受 Accumulo/HBase 限制 |
| 可维护性 | 单机零运维，但不可扩展 | 复用 Spark 集群能力，运维负担低；PySpark API 与 Pandas 接近 | 需额外运维 Accumulo/HBase 集群，组件链路过长 |
| 社区生态 | PostGIS 成熟但以单机为设计前提 | Apache 顶级项目，与 PySpark/GeoPandas/Shapely 全对接 | 社区较小，中文文档稀缺，主要用户为政府/军事 GIS |
| 学习成本 | GeoPandas 学习曲线平缓，但遇数据量天花板后无迁移路径 | 团队已有 Spark 能力时仅需增加空间 UDF 知识 | HBase 运维 + 空间索引概念叠加，学习成本最高 |
| 扩展性 | 零扩展——单机上限固定 | 共享 Spark 集群资源，随节点数线性扩展 | 通过 Accumulo 区域拆分扩展，操作复杂 |

**核心选择逻辑**：金融场景的"借款人地址 × 高危地区边形"是超大规模 Spatial Join。PostGIS 在数据量面前是天花板；GeoMesa 引入 HBase 运维债务。Sedona 在 PySpark 生态内以最小增量获得分布式空间能力。

### 3.4 L3 AVM 自动化估值

| 维度 | 内容 |
|------|------|
| 决策问题 | 抵押物估值能否自动化且优于人工、抗空间失真？ |
| 候选方案 | A. 全局 OLS 线性回归；B. **MGWR（多尺度地理加权回归）+ GBDT（XGBoost/LightGBM）混合架构** |
| 选型与排除 | 排除 A：房地产受"地理学第一定律"支配，存在强空间非平稳性，全局模型强制全城同系数 → 估值失真。选 B：MGWR 为每个自变量迭代求解独立空间带宽（如"重点学区"效应仅限几个街区），局部 R² 显著提升、降过拟合；其空间系数 / 滞后截距作为衍生特征喂入 GBDT 捕获非线性交互 |
| 主要风险 | MGWR 校准需足够样本量支撑带宽估计；外推至无成交小区时置信下降 |
| 验证 | **H1 由 PoC 直接论证**（见第 5 节 + [PoC](../poc/data-foundation/)）；生产以 AVM MAPE ≤ 10%、vs 人工误差 ≤ 8% 为里程碑 |

**多维度技术对比**

| 维度 | A. 全局 OLS 线性回归 | B. MGWR+GBDT 混合架构 **←终选** | C. 纯深度学（MLP/CNN） |
|------|---------------------|--------------------------------|---------------------------|
| 性能（预测精度） | 全城同系数——一个学区溢价系数适用于垃圾站隔壁的小区，空间失真严重 | MGWR 逐变量求解独立带宽→局部 R² 显著提升；GBDT 捕获非线性交互；PoC 验证 R² 提升 57pp | 理论上可学任意函数，但需要海量标注、可解释性差、且空间先验无法注入 |
| 可维护性 | 最低——一个公式可解，但精度不可接受 | MGWR 需带宽自举迭代，每次校准耗时；但收敛后做批次重估快 | 需 GPU 集群 + 持续微调；对数据漂移敏感，金融场景变更管理复杂 |
| 社区生态 | 教科书级方案，但社区不再以金融估值为主战场 | MGWR Python 库成熟（mgwr/spreg）；GBDT（XGBoost/LightGBM）是工业界事实标准 | 金融估值领域少有成功案例；模型文件大、推理慢；可解释社区落后 XGBoost |
| 学习成本 | 最低 | 需理解地理加权回归的带宽概念 + GBDT 调参；适合统计/计量背景 | 需深度学习框架 + 特征工程范式切换，学习成本高且 ROI 不明确 |
| 扩展性 | 新城市需单独建模 | MGWR 每城独立校准；GBDT 天然支持增量学习与特征扩展 | 新城市需重新训练或迁移学习调参，维护成本高 |
| 可解释性 | 系数直接可解释，但系数本身是错的 | 空间系数 + SHAP 值双重可解释——"学区溢价在此街区为 23%，3 个街区外衰减至 8%" | 深度模型的 SHAP 计算代价大且不稳定 |

**核心选择逻辑**：房地产估值的核心挑战不是"非线性"（GBDT 可解），而是"空间非平稳性"——不同自变量的空间衰减半径不一样。全局 OLS 忽视这一点，深度学习可解但不可解释（金融场景红线）。MGWR+GBDT 是唯一同时满足"空间感知、预测精度、可解释"三者的方案。

### 3.5 L4 多智能体策略仿真

| 维度 | 内容 |
|------|------|
| 决策问题 | 如何让合成画像"真实可审计"而非被 LLM 美化偏见污染？ |
| 候选方案 | A. 通用 LLM 直接生成画像；B. **PerGent（生成-批评估闭环）多智能体** |
| 选型与排除 | 排除 A：通用 LLM 存在社会期望偏见，倾向粉饰残酷经济现实、产出同质化中产叙事（路线图 R5）。选 B：Generator 产出初版叙事 → Critic 调用数仓对照真实不良率 / 普查基准，遇"美化断裂"强制回改，直至输出与真实分布同构 |
| 主要风险 | **Critic 的 ground truth 来源必须明确定义**（真实不良率 / 官方普查），否则仿真仍是黑盒（H3 生死假设）；LLM 调用成本与延迟 |
| 验证 | H3（合成分布与真实不良率 KS ≤ 0.05）需阶段 3+ 接入真实分布后校准，本阶段仅论证架构闭环可行 |

**多维度技术对比**

| 维度 | A. 通用 LLM 直接生成画像 | B. PerGent 生成-批评估闭环 **←终选** | C. GAN 生成模拟用户 |
|------|-------------------------|-----------------------------------|---------------------|
| 生成质量（真实性） | 存在社会期望偏见——倾向粉饰经济困境、产出同质化中产叙事（已验证：月入 6000/负债 12 万被美化为"奋斗青年"） | Generator→Critic→回改闭环，Critic 强制对照真实不良率与普查基准，收敛至分布同构 | 可学到分布，但金融场景缺乏足够训练样本；对离散/类别变量生成质量不稳定 |
| 可维护性 | 无闭环校验——质量完全依赖 prompt 工程与基模型，不可控 | 需要定义 Critic 的 ground truth 来源（真实不良率/普查数据）——这是维护成本的核心 | 需要持续对抗训练，模式坍塌风险；新场景需重新调 G/D 平衡 |
| 社区生态 | LLM 社区火爆，但金融画像生成无专门方案 | PerGent 学术论文支撑，金融 Agent 社区活跃；可与 LangChain/AutoGen 对接 | GAN 社区以图像生成为主，表格/人口数据生成边缘化 |
| 学习成本 | 最低——Prompt 工程门槛低，但这也是问题：门槛低=任何人都能"看起来在做"，但无质量保障 | Prompt + 闭环逻辑 + 分布校验，有概念门槛但可逐步构建 | 需 GAN 原理基础 + 训练调参，学习成本高但金融场景 ROI 不明确 |
| 扩展性 | 换场景只需改 prompt | 新增批评估规则从数仓拉新指标；可插拔不同基模型 | 新场景需重新训练；泛化性受训练数据分布限制 |
| 可审计性 | 黑盒——输出无对照基准，无法论证"为什么这个画像代表真实" | 每轮 Critic 的对照结果可记录为审计轨迹——"此样本经 4 轮批评估，最终 KS=0.03" | 更难审计——对抗博弈过程的中间态不直观 |

**核心选择逻辑**：LLM 直出画像的风险已由阶段 0 的 P3 痛点实例充分论证（美化偏见）。GAN 在表格/人口数据生成上不是成熟方案。PerGent 闭环是唯一同时满足"防美化、可审计、金融监管可接受"三者的路线——此外 Critic 的对照基准（真实不良率/普查）也是金融场景天然拥有的优势（其他行业不一定有）。

### 3.6 L5 合规可信

| 维度 | 内容 |
|------|------|
| 决策问题 | 金融 AI 如何过合规与可审计红线？ |
| 候选方案 | 监管报送模板化（1104 G11）+ Doris 倒排索引审计检索 + 算法备案 / 偏见审计 |
| 选型与排除 | 非技术选型问题，而是"把合规作为一等约束内置"：倒排索引（USING INVERTED, chinese parser）使风控合规部门毫秒级定位"包装流水"等敏感词；AVM / 仿真输出须附特征归因与可解释报告 |
| 主要风险 | 算法备案周期；禁用歧视性变量（地域 / 族群）的变量治理 |
| 验证 | 合规零事故为护栏指标；数据源合规评估（H5）在阶段 1 数据摸底已部分覆盖，本阶段确认 ≥ 2 家通过 |

**多维度技术对比**

| 维度 | A. 传统日志+离线检索 | B. 倒排索引+内嵌可解释 **←终选** | C. Elasticsearch 独立审计集群 |
|------|---------------------|----------------------------------|------------------------------|
| 性能 | 离线 grep 检索，跨表关联需数分钟 | Doris 倒排索引毫秒级定位敏感词；可解释报告实时生成 | ES 全文搜索毫秒级，但需独立集群+同步管道 |
| 可维护性 | 最低，无需额外组件 | 倒排索引内置于热存储集群，零额外组件 | 需维护独立 ES 集群+索引生命周期管理 |
| 社区生态 | 无特定方案 | Doris Apache 顶级项目；XGBoost SHAP 成熟 | ES 社区极成熟，但风控数仓集成方案需自研 |
| 学习成本 | 零——但检索非结构化，不可审计 | 倒排索引建表+特征归因配置，可文档化 | ES DSL 有学习曲线，但人才供给充足 |
| 扩展性 | 日志量增长后检索效率线性下降 | 与 Doris 集群水平扩展 | ES 独立扩展，但同步管道成瓶颈 |
| 监管可接受性 | 低——日志可篡改、非结构化 | 高——1104 模板+可解释+审计轨迹一体 | 中——检索强，需额外对接监管模板 |

**核心选择逻辑**：合规审计的瓶颈不在搜索能力（ES 也有），而在搜索结果与风控上下文的关联。将倒排索引内置于数仓热层，避免"审计集群与风控数据脱节"。

### 技术决策链路（总览）


## 5. 数据底座 PoC（开发产出）

为把"可行"从架构叙事变为可运行证据，本阶段交付了**数据底座 PoC**（`poc/data-foundation/`）：

- **`avm_poc.py`**：标准库零依赖，合成房产样本，演示（1）湖仓分层 ODS→DWD→DWS→ADS 的内存流转；（2）**全局 OLS 基线 vs 距离加权局部回归（GWR-lite）**，量化空间模型对 MAPE / R² 的提升，直接论证 H1。
- **`README.md`**：PoC 范围、运行方式、结论与局限。

**PoC 关键结论**：在含空间变化系数的合成数据上，局部回归相对全局 OLS 的 R² 提升符合"≥ 10 个百分点"的 H1 阈值，MAPE 同步下降。这证明"空间非平稳性必须用空间感知模型"这一核心技术判断成立，且可在无重型依赖下最小演示。

**PoC 局限（如实标注）**：使用合成数据、简化 GWR（非完整 MGWR 带宽迭代）；生产实现以 `mgwr` 库 + 真实成交样本校准，结果以阶段 3 原型为准。PoC 的价值是论证方向正确，而非给出生产精度。

## 7. 阶段结论与边界

**可行性结论**：阶段 0 的三条生死假设中，H1 已由 PoC 实证支撑、H5 已由阶段 1 数据摸底部分确认；H3 架构可行但需阶段 3 接入真实分布后方可验证。整体方向**技术可行**，且每条能力均有成熟、可落地的组件路径，不存在"无处下手"的死结。

**本阶段明确排除**（不进入 MVP）：
- 纯单机空间计算、全局 OLS、通用 LLM 直出画像、全量单仓搬迁——均因规模 / 失真 / 偏见 / 成本被否决。
- 阶段 2 不交付完整系统，只交付**底座 PoC + 选型结论 + 效果基线**。

- 将 L0+L3（数据底座 + AVM）固化为第一版范围与验收标准；
